# План реалізації дипломної роботи

**Тема (орієнтовна):** «Розробка вебсистеми обробки даних та дослідження методів підвищення її продуктивності за допомогою серверів додатків Laravel Octane»

Цей файл є робочим планом для Claude Code. Його треба покласти в новий репозиторій як `docs/PLAN.md`, а короткі правила роботи винести в `CLAUDE.md` (шаблон наприкінці). Етапи виконуються по черзі. Кожен етап закінчується окремим PR, який автор переглядає і зливає.

## 0. Ключова ідея і принцип чесного порівняння

Один і той самий код застосунку (один Docker-образ на базі однієї версії PHP і тих самих розширень) запускається в чотирьох режимах:

| Режим | Що всередині | Порт |
|---|---|---|
| `fpm` | Nginx + PHP-FPM (класична модель Share-Nothing) | 8081 |
| `roadrunner` | Laravel Octane + RoadRunner | 8082 |
| `swoole` | Laravel Octane + Swoole | 8083 |
| `frankenphp` | Laravel Octane + FrankenPHP | 8084 |

Відрізняється тільки точка входу (entrypoint), а не код. Інакше результати не можна буде порівнювати.

Обов'язкові умови для кожного прогону:
- однакові ліміти: `cpus: 1.0`, `mem_limit: 512m` на контейнер застосунку;
- PostgreSQL і Redis мають власні (однакові для всіх режимів) ліміти і **не входять** у 1 vCPU застосунку;
- одночасно під навантаженням працює **тільки один** режим (інші контейнери зупинені);
- `APP_ENV=production`, `APP_DEBUG=false`, OPcache увімкнено, `config:cache`, `route:cache`, `event:cache`;
- ліміт 512 MB орієнтовний: якщо котрийсь режим упирається в пам'ять, ліміт піднімається однаково для всіх і це фіксується в `bench/config.md`;
- однакова кількість воркерів відносно CPU (базово: FPM `pm.max_children` і Octane `--workers` підбираються окремим калібрувальним прогоном, фінальні значення фіксуються в `bench/config.md`);
- прогрів (warm-up) 30 с перед вимірюванням, кожен сценарій повторюється мінімум 3 рази, у звіт іде медіана;
- генератор навантаження k6 не повинен «з'їдати» CPU застосунку: окремий контейнер з закріпленими ядрами (`cpuset`) або окрема машина.

## 3. Етапи

### Етап 1. Каркас проєкту і Docker-стенд
**Кроки**
1. Створити Laravel 12 у `app/`, встановити `laravel/octane`, `spiral/roadrunner-cli`, `spiral/roadrunner-http`.
2. Один `docker/php/Dockerfile` (multi-stage): PHP 8.4 + розширення `pdo_pgsql`, `redis`, `opcache`, `pcntl`, `sockets`, `swoole`; бінарник `rr`.
3. Для FrankenPHP окремий `docker/frankenphp/Dockerfile` на офіційному образі `dunglas/frankenphp` з тими самими розширеннями і тією ж мінорною версією PHP (вбудувати Swoole і FrankenPHP в один образ складно, тому це виняток з правила «один образ»; версії фіксуються в `bench/config.md`).
4. `docker-compose.yml` з профілями `fpm`, `roadrunner`, `swoole`, `frankenphp`; сервіси `db` (PostgreSQL), `redis`; ліміти ресурсів.
5. Скрипти для Windows і Linux: `Makefile` + `scripts/*.ps1` (або тільки `docker compose`-команди в README): up-fpm, up-rr, up-swoole, up-franken, seed.
6. README з розділом «Windows»: Docker Desktop з бекендом WSL2, репозиторій клонується **всередину файлової системи WSL** (`\\wsl$\Ubuntu\home\...`), а не на `C:\`, бо інакше файловий I/O буде в рази повільнішим і зіпсує результати FPM.

**Критерії готовності**
- `curl localhost:808{1,2,3,4}/api/ping` повертає однаковий JSON у всіх чотирьох режимах.
- Стенд піднімається на Windows 11 + Docker Desktop (WSL2) за інструкцією з README.
- `docker stats` показує ліміт 1 CPU / 512 MB для контейнера застосунку.
- README описує запуск з нуля однією-двома командами.

### Етап 2. Предметна область «Облік цифрових документів / звітів»
**Кроки**
1. Моделі й міграції: `Counterparty` (контрагент), `Template` (шаблон документа), `Order` (замовлення), `OrderItem`, `Document` (згенерований документ/звіт), `Product` за потреби. Зв'язки: Counterparty 1:N Order, Order 1:N OrderItem, Template 1:N Document, Order 1:N Document.
2. Індекси під запити сценарію 2.
3. Детермінований сидер з фіксованим seed: орієнтовно 5 000 контрагентів, 200 шаблонів, 100 000 замовлень, 500 000 позицій (обсяг уточнюється, див. питання).
4. Автентифікація: Laravel Breeze (Blade) для входу у вебінтерфейс, Sanctum для API-токенів. Ролі мінімальні (admin, manager).
5. Базовий CRUD API (REST) для документів і замовлень, щоб система була «прикладною», а не лише набором бенч-роутів.
6. Генерація файлів PDF/DOCX **не потрібна**. «Документ» це запис з даними звіту (JSON), який можна переглянути в інтерфейсі і завантажити як CSV/JSON.

**Критерії готовності**
- `php artisan migrate:fresh --seed` відпрацьовує за прийнятний час і дає однакові дані при повторі.
- Feature-тести на CRUD і автентифікацію проходять.

### Етап 2а. Вебінтерфейс для демонстрації
**Кроки**
1. Сторінки (Blade + Tailwind): вхід, дашборд, список і картка контрагента, список і картка замовлення, шаблони, документи/звіти (перегляд, «згенерувати звіт», експорт CSV).
2. Сторінка «Бенчмарки»: завантажує зведений CSV з `analysis/` і показує інтерактивні графіки Chart.js (RPS, p95, RAM за режимами). Це головна сторінка для показу на захисті.
3. Сторінка «Про стенд»: схема архітектури і поточний режим сервера (FPM / RoadRunner / Swoole / FrankenPHP), щоб наочно показати, що це той самий застосунок.

**Критерії готовності**
- Усі сторінки працюють у всіх чотирьох режимах.
- На сторінці «Бенчмарки» відображаються реальні результати хоча б одного прогону.

### Етап 3. Чотири типи контролерів (сценарії навантаження)
| # | Роут | Що робить | Що вимірює |
|---|---|---|---|
| 1 | `GET /api/ping` | легкий JSON без БД і кешу (публічний) | накладні витрати bootstrap фреймворку |
| 1а | `GET /api/me` | те саме, але через Sanctum-токен | вартість автентифікації |
| 2 | `GET /api/orders/{id}/report`, `GET /api/counterparties/{id}/orders?with=items,documents` | Eloquent із `with()`, JOIN, агрегати, пагінація | ORM + мережа до БД |
| 3 | `GET/POST /api/stats/{key}` | читання й запис агрегованих даних у Redis (лічильники, хеші, TTL) | швидкий I/O |
| 4 | `POST /api/reports/prepare` | генерація і серіалізація великого масиву (наприклад, 10–50 тис. рядків) у JSON | CPU-bound робота |

**Кроки**
1. Реалізувати контролери в `App\Http\Controllers\Bench`.
2. Сценарії 2–4 вимагають Sanctum-токен (k6 отримує токени тестових користувачів перед прогоном). Публічний ping лишається для «чистого» виміру фреймворку.
3. Параметризувати розмір навантаження (кількість рядків, глибина зв'язків) через query-параметри з розумними межами.
4. Feature-тести: однакова відповідь у всіх режимах (порівняння хешу тіла відповіді).

**Критерії готовності**
- Усі сценарії відповідають у всіх чотирьох режимах, тіла відповідей ідентичні.
- Жодного стану між запитами в коді контролерів (перевіряється етапом 6).

### Етап 4. Сценарії k6
**Кроки**
1. `bench/k6/*.js` для кожного сценарію + `mixed.js` (наприклад, 40% ping, 30% db, 20% cache, 10% compute).
2. Ступінчасте навантаження: 10 → 50 → 100 → 200 → 300 → 500 → (800, 1000 для пошуку межі) VU, кожна сходинка 60 с.
3. Окремо: тест з постійною частотою запитів (`constant-arrival-rate`) для вимірювання затримок при однаковому RPS.
4. `soak.js`: 30–60 хв помірного навантаження для аналізу пам'яті.
5. Порогові значення (`thresholds`): частка помилок < 1%, фіксація p95/p99.
6. `bench/run.sh`: цикл режим × сценарій × повтор, зупинка інших контейнерів, прогрів, збереження JSON у `bench/results/<дата>/<режим>/<сценарій>-<n>.json`.

**Критерії готовності**
- Одна команда `./bench/run.sh` проводить повний експеримент без ручних дій.
- Результати кожного прогону зберігаються разом із метаданими (git sha, параметри воркерів, версії).

### Етап 5. Моніторинг ресурсів
**Кроки**
1. Профіль `monitoring`: cAdvisor + Prometheus + Grafana (готовий дашборд у репо).
2. Експорт CPU та RAM контейнера застосунку за час прогону в CSV (через Prometheus API).
3. Для Octane додатково: пам'ять кожного воркера (`memory_get_usage` у middleware/ендпоінті `/api/_debug/memory`, доступному лише в бенч-режимі).

**Критерії готовності**
- Для кожного прогону є часовий ряд CPU % і RAM MB поряд з k6-метриками.

### Етап 6. Дослідження витоків пам'яті і стану
**Кроки**
1. Свідомо створити «погані» приклади (за фіче-флагом `BENCH_LEAK_DEMO=true`):
   - статичний масив, що накопичує дані між запитами;
   - синглтон, у який інжектовано `Request` або користувача (витік стану між запитами);
   - кеш у властивості сервісу без очищення.
2. Показати на soak-тесті ріст пам'яті воркера і хибні дані в відповідях.
3. Показати виправлення: `scoped` замість `singleton`, `Octane::flush`/`flush`-масив у `config/octane.php`, `--max-requests`, слухачі `RequestTerminated`, уникання статичного стану.
4. Написати `docs/memory-leaks.md` з практичними рекомендаціями (цей текст ляже в розділ диплому).

**Критерії готовності**
- Є графік «пам'ять воркера від кількості запитів» до і після виправлення.
- Є тест, що ловить витік стану між двома запитами в Octane.

### Етап 7. Аналіз і графіки
**Кроки**
1. `analysis/parse.py`: k6 JSON + Prometheus CSV → зведена таблиця (режим, сценарій, VU, RPS, p50, p95, p99, помилки, CPU, RAM).
2. `analysis/plots.py`: графіки
   - RPS від кількості VU для кожного сценарію (3 лінії: FPM, RR, Swoole);
   - p95/p99 затримки від VU;
   - RAM і CPU під навантаженням;
   - стовпчикова діаграма приросту відносно FPM;
   - пам'ять воркерів у soak-тесті.
3. Таблиці у форматі Markdown/LaTeX/CSV для вставки в текст.

**Критерії готовності**
- Одна команда будує всі графіки з `bench/results/` у `analysis/figures/` (PNG 300 dpi + SVG).

### Етап 8. Економічний ефект
**Кроки**
1. Взяти максимальний стабільний RPS (p95 < порогу, помилки < 1%) для кожного режиму.
2. Порахувати, скільки інстансів 1 vCPU / 512 MB потрібно для цільового трафіку (наприклад, 1 000 / 5 000 RPS).
3. Помножити на ціни 2–3 хмарних провайдерів (дата фіксації цін вказується).
4. `docs/economics.md` з таблицею і висновком.

**Критерії готовності**
- Таблиця «режим → кількість інстансів → вартість на місяць → економія відносно FPM».

### Етап 9. Документація і матеріали для тексту диплому
**Кроки**

**Критерії готовності**

## 5. Ризики

- **Docker Desktop на Windows** (обрано автором) працює через WSL2-віртуалку, тому абсолютні числа будуть нижчими і «шумнішими», ніж на чистому Linux. Для диплому це прийнятно, бо порівнюються режими між собою в однакових умовах. Що зробити: бекенд WSL2, код у файловій системі WSL, ноутбук від мережі живлення з режимом «Максимальна продуктивність», закрити важкі програми, не менше 3 повторів, у `.wslconfig` виділити WSL фіксовану кількість ядер і пам'яті. Ці умови описуються в методиці як обмеження дослідження.
- **k6 на тій самій машині** конкурує за CPU. Рішення: `cpuset` для застосунку і k6 на різних ядрах.
- **БД стає вузьким місцем** у сценарії 2 і нівелює різницю між режимами. Це теж результат, але його треба пояснити; БД дати достатньо ресурсів.
- **Swoole і деякі пакети** (наприклад, з глобальним станом) несумісні. Мінімізувати сторонні пакети.
- **Хмарне середовище Claude Code** не дає надійних чисел для бенчмарків. Код і smoke-тести пишуться там, а фінальні вимірювання автор запускає на своїй машині.

## 6. Шаблон `CLAUDE.md` для репозиторію

```markdown
# Diploma: Laravel Octane benchmark

- План: docs/PLAN.md. Працюй по етапах, один етап = один PR.
- Мова коментарів і документації: українська; код та ідентифікатори англійською.
- Код застосунку один для всіх режимів. Не додавай логіку, що залежить від режиму, крім entrypoint.
- Жодного статичного/глобального стану в контролерах і сервісах (Octane).
- Перед PR: `docker compose run --rm app php artisan test` і smoke `k6 run --vus 5 --duration 10s`.
- Не коміть результати великих прогонів у git, тільки зведені CSV і графіки.
```

## 7. Рішення автора (2026-11-03)

1. БД: PostgreSQL.

6. FrankenPHP додається четвертим режимом.
7. Текст диплому поки не пишемо.
