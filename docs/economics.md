# Економічний ефект

Розрахунок відповідає на питання: скільки однакових серверів (1 vCPU, 512 MB) потрібно, щоб обслужити заданий
трафік у кожному режимі, і скільки це коштує на місяць.

## Методика

1. **Стабільна пропускна здатність одного інстансу.** Для кожного режиму і сценарію береться найбільший RPS
   серед рівнів VU, на яких p95 < 500 мс і частка помилок < 1%. Рівні з більшим навантаженням, де затримки
   або помилки виходять за поріг, не враховуються: сервер, що відповідає за 3 секунди, у продакшні непридатний.
2. **Запас потужності.** Сервери не завантажують на 100%: у розрахунку використовується 70% стабільного RPS
   (`--headroom 0.7`), щоб витримати піки.
3. **Кількість інстансів** = ⌈цільовий RPS / (стабільний RPS × 0.7)⌉ для цілей 1 000 і 5 000 RPS.
4. **Вартість** = інстанси × місячна ціна інстансу у 2–3 провайдерів (`analysis/prices.json`).
5. **Економія** відносно PHP-FPM = 1 − інстанси режиму / інстанси FPM.

Основний сценарій для розрахунку `mixed` (змішаний профіль, найближчий до реального трафіку). Для порівняння
можна порахувати окремо легкі (`ping`) і важкі (`database`) запити.

```bash
python3 analysis/economics.py analysis/results/<дата>                       # mixed
python3 analysis/economics.py analysis/results/<дата> --scenario database   # інший сценарій
python3 analysis/economics.py analysis/results/<дата> --p95 300 --targets 1000 5000 10000
```

Результат: `analysis/figures/<дата>/economics.md` (таблиці), `economics-instances.png/svg` (графік) і
`analysis/results/<дата>/economics.csv`.

## Ціни

`analysis/prices.json` містить **приклади** цін інстансів, найближчих до стенду. Перед використанням у дипломі:

1. Перевірте актуальні ціни на сайтах провайдерів.
2. Вкажіть дату перевірки в полі `checked_at`.
3. За потреби додайте провайдера, що використовується в Україні, або ціну в гривнях.

Конфігурації провайдерів не ідентичні стенду (наприклад, burst-CPU у AWS t4g або більше пам'яті у Hetzner).
Це варто згадати в тексті: розрахунок показує порядок економії, а не точну суму.

## Обмеження розрахунку

- Лінійне масштабування: припускається, що N інстансів за балансувальником дають N × RPS одного. Насправді
  спільна БД стає вузьким місцем раніше, особливо у сценарії `database`.
- Не враховуються вартість БД, Redis, балансувальника і трафіку: вони однакові для всіх режимів.
- Не враховуються витрати на адаптацію коду до Octane (аудит стану, тести, див. `docs/memory-leaks.md`).
  Для невеликих проєктів ці витрати можуть перевищити економію на серверах.
- Вимірювання проведені на ноутбуці у WSL2: абсолютні RPS нижчі, ніж на сервері, тому кількість інстансів
  завищена для всіх режимів однаково. Відносна економія при цьому зберігається.
