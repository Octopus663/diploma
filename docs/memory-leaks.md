# Витоки пам'яті і стану в Laravel Octane: практичні рекомендації

Цей документ є основою підрозділу диплому про роботу воркерів у пам'яті. Код прикладів лежить у
`app/app/LeakDemo/`, маршрути `/api/leak/*` вмикаються змінною `BENCH_LEAK_DEMO=true`, експеримент
запускається скриптом `bench/leak.sh`.

## 1. Чому проблема з'являється саме в Octane

У PHP-FPM діє модель **Share-Nothing**: для кожного HTTP-запиту фреймворк завантажується заново, а після
відповіді весь стан процесу (статичні властивості, синглтони, об'єкти) знищується. Помилка в управлінні
станом живе рівно один запит.

Octane завантажує застосунок **один раз на воркер** і обробляє ним тисячі запитів. Перед кожним запитом
Octane клонує контейнер (sandbox) і скидає відомі йому частини стану (запит, сесію, автентифікацію,
`scoped`-прив'язки), але не може знати про стан, який створив сам розробник. Усе, що пережило запит,
переходить у наступний:

| Що | PHP-FPM | Octane |
|---|---|---|
| Статичні властивості класів | очищаються після запиту | живуть увесь час воркера |
| Синглтони, створені в `boot()` або через `octane.warm` | створюються на кожен запит | один екземпляр на воркер |
| Синглтони, створені під час запиту | живуть один запит | живуть один запит (sandbox), але є винятки* |
| `scoped`-прив'язки | один запит | скидаються Octane після кожного запиту |
| Глобальні змінні, `$_SERVER` змінений вручну | один запит | живуть увесь час воркера |

\* Якщо синглтон, створений під час запиту, зберігається у статичній властивості або в об'єкті, що належить
базовому застосунку, він також переживе запит.

## 2. Три типові антипатерни (відтворені в коді)

### 2.1. Статичний масив, що накопичує дані

```php
class StaticCollector
{
    public static array $events = [];

    public static function record(array $event): int
    {
        static::$events[] = $event;   // в Octane масив росте з кожним запитом
        return count(static::$events);
    }
}
```

Маршрут `/api/leak/static` додає близько 10 КБ на запит. У PHP-FPM пам'ять стабільна, в Octane росте
лінійно до перезапуску воркера або до `memory_limit` (фатальна помилка, 502 для клієнта).

**Виправлення** (`/api/leak/fixed/static`): не зберігати дані запиту в статичних властивостях. Якщо дані
треба накопичувати між запитами, вони йдуть у Redis або БД.

### 2.2. Синглтон з інжектованим `Request`

```php
$this->app->singleton('leak.context.singleton', fn ($app) => new RequestContext($app['request']));
// і десь у boot() або octane.warm:
$this->app->make('leak.context.singleton');
```

У PHP-FPM синглтон створюється для кожного запиту і бачить правильні дані. В Octane він створюється один
раз і назавжди тримає **запит, з яким воркер стартував**. Усі наступні користувачі бачать чужі дані: це
вже не лише витік пам'яті, а витік інформації між користувачами.

Результат `bench/leak.sh` (стан синглтона після запитів `?name=alice`, `bob`, `carol`):

| Режим | Повертає |
|---|---|
| PHP-FPM | alice, bob, carol (правильно) |
| RoadRunner, Swoole, FrankenPHP | anonymous, anonymous, anonymous (дані старого запиту) |

**Виправлення** (`/api/leak/fixed/singleton`):

- `scoped()` замість `singleton()`: Octane скидає такі екземпляри після кожного запиту;
- передавати `Request` у метод, а не в конструктор (`public function handle(Request $request)`);
- якщо сервісу потрібен запит, інжектувати контейнер і брати `$this->app['request']` у момент виклику,
  або використовувати резолвер `fn () => request()`.

### 2.3. Необмежена мемоізація у властивості сервісу

```php
class ReportMemo
{
    private array $memo = [];

    public function get(string $key): string
    {
        return $this->memo[$key] ??= $this->build($key);   // кожен новий ключ лишається назавжди
    }
}
```

Мемоізація виглядає безпечно, але в довгоживучому синглтоні масив росте з кожним новим ключем
(`/api/leak/memo`).

**Виправлення** (`/api/leak/fixed/memo`): обмежити розмір (LRU), задати TTL або винести кеш у
`Cache` (Redis) з власною політикою витіснення.

## 3. Результати експерименту

`bench/leak.sh` запускає кожен режим з одним воркером, відправляє запити пакетами по 1000 і після кожного
пакета записує пам'ять воркера (`memory_get_usage()`) і контейнера. Графіки будує `analysis/plots.py`
(`analysis/figures/leak-*.png`).

Попередній прогін у хмарному середовищі (4 000 запитів, 1 воркер, без `--max-requests`), пам'ять воркера, МБ:

| Режим | `static` старт → 4 000 | `fixed/static` | `memo` старт → 4 000 | `fixed/memo` |
|---|---|---|---|---|
| PHP-FPM | 0.8 → 0.8 | 0.8 → 0.8 | 0.8 → 0.8 | 0.8 → 0.8 |
| RoadRunner | 8.4 → 56.9 | 8.4 → 8.4 | 8.3 → 55.5 | 8.4 → 9.6 |
| Swoole | 19.7 → 68.1 | 19.7 → 19.7 | 19.7 → 66.9 | 19.7 → 20.9 |
| FrankenPHP | 5.7 → 54.2 | 5.7 → 5.7 | 5.6 → 52.8 | 5.7 → ~6.8 |

Витік дає ≈ +12 МБ на кожні 1 000 запитів у всіх трьох серверах Octane і не проявляється в PHP-FPM
(там пам'ять процесу скидається після кожного запиту). Виправлені варіанти стабільні; обмежена
мемоізація зупиняється на 100 записах (~1 МБ).

Для диплому прогін треба повторити на робочій машині (`./bench/leak.sh`, 20 000 запитів) і взяти
числа з `bench/results/leak-<дата>/memory.csv`.

## 4. Рекомендації

1. **Не зберігайте стан запиту в статичних властивостях і глобальних змінних.** Перевірка: пошук по коду
   `static \$`, `global `, `$GLOBALS` у сервісах і контролерах.
2. **Не інжектуйте `Request`, `Repository` конфігурації чи `Application` у конструктори синглтонів.** Octane
   документує це як основне джерело помилок. Використовуйте `scoped()` або передавайте залежність у метод.
3. **Обережно з `octane.warm` і з `make()` у `boot()`.** Все, що створено при старті воркера, живе до його
   перезапуску.
4. **Мемоізація лише з обмеженням.** LRU, TTL або зовнішній кеш.
5. **`--max-requests` як страховка, не як рішення.** Перезапуск воркера після N запитів (у стенді 500)
   обмежує ріст пам'яті «пилкою», але ховає помилку і додає затримку на старт нового воркера.
   Порівняння: `MAX_REQUESTS=500 ./bench/leak.sh`.
6. **`config/octane.php`:** у масив `flush` додавайте власні сервіси, які мають скидатися між запитами;
   слухачі `RequestTerminated` / `OperationTerminated` дозволяють прибрати стан вручну.
7. **Сторонні пакети.** Перевіряйте пакети на сумісність з Octane: багато з них кешують стан у статичних
   властивостях (наприклад, старі версії пакетів для мультитенантності, локалізації, логування).
8. **Тести.** Feature-тест у Laravel обробляє кілька запитів одним екземпляром застосунку, як воркер Octane.
   Тест «два запити різних користувачів поспіль повертають різні дані» ловить витоки стану
   (`tests/Feature/LeakDemo/LeakDemoTest.php`). `scripts/smoke.sh` додатково перевіряє це на живому стенді:
   поперемінні запити `bench01` і `bench02` до `/api/me` мають повертати кожному свій профіль.
9. **Моніторинг.** Стежте за пам'яттю воркерів (дашборд Grafana, `/api/_debug/memory` у тестовому
   середовищі). Лінійний ріст при стабільному навантаженні майже завжди означає витік.

## 5. Що в цьому застосунку зроблено для безпечної роботи в Octane

- Сервіси (`OrderService`, `DocumentService`, `ReportQuery`, `ReportCompute`, `CounterpartyStatsCache`)
  не мають властивостей зі станом запиту; залежності лише через конструктор без `Request`.
- `ReportCompute` використовує власний генератор випадкових чисел замість глобального `mt_rand()`, щоб
  результат не залежав від того, що виконував воркер до цього.
- Демонстраційні антипатерни ізольовані у `App\LeakDemo` і реєструються лише за прапорцем.
